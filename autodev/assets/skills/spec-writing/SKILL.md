# 规范化软件研发文档编写技能 (Spec Writing)

## 1. 需求规格说明书 (SRS — EARS 句式)
- 每条功能需求必须具备唯一编号 `REQ-001`、`REQ-002`…，非功能需求使用 `NFR-001`…。
- 正文统一使用 **EARS (Easy Approach to Requirements Syntax)** 无歧义句式：
  - 事件驱动：`当 <触发事件> 发生时，系统应 <确定的系统响应>。`
  - 状态驱动：`在 <特定前置状态> 期间，系统应 <持续保持的行为>。`
  - 异常条件：`若 <异常或越界输入> 出现，则系统应 <返回错误码并安全回滚>。`
- 每条 `P0` 需求必须给出可自动化验证的验收判据。

## 2. 架构设计文档 (ADD & MADR)
- 遵循 **arc42** 精简结构：系统上下文 → 容器/模块划分 → 跨模块契约策略 → 运行时关键链路 → 非功能保障。
- 架构图使用合法的 `mermaid` 代码块（`flowchart TD` / `sequenceDiagram`），包含特殊括号的节点文本务必加双引号（如 `gw["API 网关 (FastAPI)"]`）。
- 关键技术选型沉淀为独立 **MADR** 记录（背景、决策、备选方案对比、影响范围）。

## 3. 模块详细设计 (Detailed Design)
- 对外接口必须写明完整签名、入参约束、返回值结构、错误码枚举以及关联的 `REQ-xxx`。
- 每个对外接口至少配套一条结构化测试用例 `TC-xxx`（标明 `unit` / `integration` / `e2e` 及覆盖的 `REQ-xxx`），确保全部 `P0` 需求在编码前已完成接口与用例双向映射。
