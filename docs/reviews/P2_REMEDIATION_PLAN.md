## 3. R1：完成回调与审批策略冲突

### 3.1 已确认现象和代码依据

Codex 在完成产物后调用 `submit_gate_result`，出现 `MCP tool call requires approval, but approval policy is never`。原生执行器恢复同一会话重试后仍无法提交终态，节点进入待确认。最终由 Vernal 的既有兼容逻辑继续执行下游校验。

这说明本轮成功依赖兼容逻辑，不代表完成协议已经正常。模型生成、会话恢复、回调等待与最终校验都贡献了耗时，不能把全部运行时间归因于模型，也不能只靠缩短轮询间隔解决。

本仓库有两条相关处理路径：

| 文件和入口 | 当前行为 | 修改关注点 |
| --- | --- | --- |
| `autodev/loopforge/bridge.py`，`poll_loopforge_run()` | 根据 `agent` 节点和错误文本中的 `submit_gate_result` 自动调用 `approve_run()`；有独立审查报告时另核对报告 | 区分正常完成、回调丢失、明确权限拒绝；不再靠错误文本决定放行 |
| `autodev/steering.py`，转向流程的运行刷新逻辑 | 对非 `approval` 且非 `human_gate` 节点做类似处理 | 当前节点类型判断更宽，必须和主执行路径使用同一规则 |
| `autodev/harnesses/loopforge_harness.py`，`_build_issue_description()` | 提示模型完成后调用终态工具 | 根据实际支持的完成协议生成提示 |
| `autodev/loopforge/bootstrap.py` | 多种 SOP 提示都要求终态工具 | 同步处理规划、编码、审查、转向等模板，不能只改一个 PM 提示 |
| `deploy/loopforge/start-runner.sh` | 启动原生 Runner，指定 Gate MCP 二进制路径 | 查清真实二进制与版本；它不是 Codex 参数的直接构造处 |

特别注意：`autodev/harnesses/cli_generic.py` 中可见的 `--approval-policy never` 位于 **DeepSeekHarness**。本轮使用的是 **LoopForge 原生 Runner 内的 Codex**，不要看到同名参数就修改这段 DeepSeek 代码。

### 3.2 先查清配置来源

保存一份脱敏的执行环境记录，至少包含服务端镜像摘要、Runner 版本与二进制摘要、Gate MCP 版本与摘要、Codex 路径及版本、SOP 版本、执行池、完成协议能力。版本命令仅使用相应二进制实际支持的参数。

在实际部署源码和运行配置中查明：Codex 启动参数由谁组装，审批策略来自哪个配置层，Gate MCP 如何注册，工具调用如何鉴权，是否存在环境变量或项目配置覆盖。只记录有效参数和脱敏配置来源，不导出凭据、会话文件或完整环境变量。

本轮没有读到该原生 Runner 的源码，也没有核对其有效合并配置。因此本文不指定未经验证的外部源码文件名、配置键或工具白名单语法。

### 3.3 推荐的修改方式

**优先修复正常完成协议，然后收紧兼容路径。**

1. 若当前 Codex 与 Runner 组合支持对指定内部工具明确授权，由部署负责人显式配置仅当前节点完成工具的必要权限。工具必须受运行身份、节点及尝试轮次限制，不能拥有批准其他项目或任意节点的能力。保留现有沙盒和其他工具审批要求。`submit_gate_result` 会写入运行状态，不能把它伪装成只读工具来规避审批。
2. 若该版本没有适用的精细权限能力，修复原生 Runner 的受控完成协议：模型提交结果，Runner 核对退出状态、当前轮产物和结构后上报节点完成，由下游校验决定能否继续。该协议需要在原生端明确实现并声明支持，不能由 Vernal 猜测完成或直接把缺失终态解释成通过。
3. 这两条路径选择一条作为正常路径。不要同时叠加多个自动批准机制。配置明确拒绝工具时，记录为环境阻塞并给出修复入口；不能在已拒绝后再换一个 API 强制完成。
4. 合并 `bridge.py` 和 `steering.py` 的完成判断，抽成共用的、可测试的策略函数。可以新增模块，但保持一个实现来源。
5. 完成消息应携带当前 `run_id`、`node_id`、`attempt`、返工轮次和产物摘要；服务端核对与当前节点一致。幂等键至少覆盖这些身份，重复上报不重复推进，迟到的上一轮消息拒收。
6. 审查节点的 `REJECT` 必须走返工，缺少当前轮审查报告不能放行。人工审批节点始终保留人工决策，完成回调不能替代规格批准或最终签收。
7. 模板调整生成新 SOP 版本，正在执行的 Run 保留原快照。恢复旧 Run 不得偷偷替换它的完成协议。

建议明确以下结果分类，名称是拟议接口，不是当前已有状态：

| 分类 | 处理 |
| --- | --- |
| `COMPLETED` | 校验当前轮证据后记录完成，继续下游 |
| `CALLBACK_MISSING` | 仅对已声明支持的恢复协议取回当前轮结果；证据不足则等待处理 |
| `CALLBACK_PERMISSION_DENIED` | 停止无效会话重试，显示权限配置冲突 |
| `ARTIFACT_INVALID` | 返回具体校验错误，进入有次数上限的返工 |
| `REVIEW_REJECTED` | 进入规定的返工目标，不得改记通过 |
| `HUMAN_APPROVAL_REQUIRED` | 保持待审批 |

旧版本只有错误字符串时，明确权限拒绝必须保守处理，未知原因不得自动放行。新增分类由执行端返回结构化原因，避免把错误措辞当协议。

### 3.4 验收

扩展 `tests/test_file_delivery.py`、`tests/test_loopforge_harness.py`、`tests/test_steering_and_global_rules.py`，覆盖：

1. 正常终态只提交一次，下一节点只启动一次。
2. 权限拒绝、未知节点类型、缺失产物、非零退出、旧轮产物，均不调用自动批准接口。
3. 人工审批节点保持等待，审查拒绝触发返工，旧审查报告不能复用为当前轮通过证据。
4. 重复回调幂等，服务重启后不重复派发，相同规则在规划和转向流程都成立。
5. 原有“只要错误字符串包含工具名就自动放行”的测试应改为上述协议测试，不能继续把宽泛放行当正确行为。

真实验收先只跑一个小型规划步骤。通过条件是无需恢复 CLI 会话重试终态工具、没有权限冲突提示、结构校验确实执行、业务产物正常回写。再验证一个审查拒绝场景和一个人工审批场景。仅作耗时观测，不承诺固定模型响应秒数。

## 4. R2：原生详情页 `adapter` 字段报错

### 4.1 已知和未知

已观察到 `Error 1054 (42S22): Unknown column 'adapter' in 'where clause'`。尚未确定是哪一个请求、数据表、查询别名或迁移导致，也未证明它影响了哪些功能。

`deploy/loopforge/compose.yaml` 的默认 LoopForge 镜像为 `ghcr.io/tencent/loopforge:0.4.0`，但环境变量可以覆盖，实际运行服务也可能在另一台机器。**默认值不等于实际部署版本。** Vernal 的本地 SQLite 工作区不是这条 MySQL 错误的修复位置。

### 4.2 定位步骤

1. 在出现提示的运行详情页记录失败请求的方法、路径、状态码、时间和请求关联号；导出内容须删除 Cookie、Authorization 和 URL 中的敏感参数。
2. 沿 `autodev/server/proxy.py` 和 `autodev/server/app.py` 的代理路径确认实际上游。只核对目的服务，不打印带凭据的配置。
3. 到该服务端按请求关联号查查询及表别名，确认错误中的 `adapter` 究竟属于哪张表或哪层 SQL。
4. 核对服务端镜像摘要、发布版本、迁移版本和实际表结构。必要时只读查询 `INFORMATION_SCHEMA.COLUMNS`，不要凭报错猜一条 `ALTER TABLE`。
5. 判断属于遗漏迁移、代码字段已改名但查询未更新、查询别名错误、还是连接错库。根因确定后再选下面的修改。

### 4.3 按证据修改

| 确认原因 | 修改方式 |
| --- | --- |
| 缺少该版本要求的字段 | 按对应源码定义补正式迁移，明确类型、索引、空值、默认值和旧数据回填；在数据库副本先验证 |
| 字段改名或查询别名错误 | 修正查询并保留项目、用户、执行器等原过滤语义，给相关组合查询补回归 |
| 代码与数据库版本不配套 | 对齐同一受支持版本和迁移，固定镜像摘要并记录升级顺序 |
| 连到错误数据库 | 修正部署连接目标，不在错误库中补字段掩盖问题 |

新增的启动检查应能区分服务存活和数据结构就绪。数据结构不兼容时明确标记不可用，不对用户展示一个无原因的空列表。可选详情面板故障可以局部提示，核心接口故障不能被吞掉。

上线前备份数据库及迁移版本，验证恢复步骤。应用回滚是否兼容新增结构要单独检查，不能把镜像回退等同于数据库回滚。不要删库、删持久卷或用空库重建来解决这一问题，也不要删掉 `WHERE adapter...` 后不保留原有过滤约束。

### 4.4 验收

失败接口在对应版本的新库和旧库升级副本均正常；迁移重跑不会重复破坏结构；旧 Run、筛选和统计仍能读取；跨用户、跨项目查询保持原权限隔离；升级失败可恢复。详情页无原报错只能算其中一项证据。

## 5. R3：区分文档过期与审批前置条件未满足

### 5.1 根因

`autodev/process/targets.py::target_is_current()` 同时判断内容哈希、文件存在性、阻塞问题和 `missions.assert_ready_for_approval()`。`autodev/process/runner.py::_hydrate_gate_row()` 把其中任一失败统一投影成 `STALE`。`autodev/server/static/js/pipeline.js` 又统一显示“内容已变更，请先在文档中心归档或重新生成”。

因此本轮质量检查正常运行时也显示文档过期。检查结束后恢复 `PENDING`，证明并非真的需要用户重写文档。只改前端文案仍无法准确区分原因。

### 5.2 修改设计

拆开两个判断，复用同一份后端评估结果：

1. **内容是否仍是审批快照**：比较文档集合、修订、哈希、磁盘内容和路径。仅该判断失败时显示文档失效或缺失。
2. **当前是否具备审批条件**：检查问题是否答完、需求评估是否对应当前输入、质量检查是否完成且有效、是否有严重问题、前置条件是否满足。执行租约仍活跃时也禁止新批准。

建议新增统一的门禁评估函数，返回如下附加字段。第一版保留现有数据库决策状态，避免为了提示改造大规模迁移历史记录。

```json
{
  "status": "PENDING",
  "content_current": true,
  "ready_for_decision": false,
  "can_approve": false,
  "blockers": [
    {
      "code": "CHECKLIST_RUNNING",
      "message": "规格质量检查正在进行，完成后可审阅批准",
      "feature_id": "001-initial"
    }
  ]
}
```

字段为拟议接口。`can_approve` 应同时考虑请求者权限；底层只计算材料与流程条件，由路由层叠加角色权限。豁免和驳回沿用各自授权及状态规则，不能由前端一个布尔值授权。

| 原因 | 用户提示与操作 |
| --- | --- |
| 目标版本已变化 | 文档已有新版本，请审阅当前版本 |
| 文件缺失或外部改动未归档 | 指明受影响文档，进入文档修订或恢复入口 |
| 问题未答 | 还有影响交付的关键问题，进入回答入口 |
| 回答后评估未完成 | 回答已保存，正在重新整理规格 |
| 检查未运行或来源已过期 | 当前版本尚未完成质量检查，可继续检查 |
| 检查运行中 | 等待当前检查完成，不提示重建文档 |
| 存在严重发现 | 展示具体发现及修订入口 |
| 前置条件未核验 | 展示缺少的核验依据 |
| 材料齐全但无审批权限 | 显示当前版本及需要的审批角色 |
| 全部满足 | 显示待审版本，允许有权限者批准 |

必须同步修改：

1. `targets.py` 提供内容检查和原因化结果。不要只把原 `target_is_current()` 变成弱检查后让旧调用者继续默认放行。
2. `runner.py` 中 `_hydrate_gate_row()`、`decide_gate()`、`is_gate_passed()` 和阶段状态推导统一使用结果；调度及任务发布同样保持全部必要检查。
3. `autodev/speckit/missions.py` 将就绪判断提取为可返回原因的函数，`assert_ready_for_approval()` 作为薄包装保留；避免调用门禁有效性又反向调用自身形成递归。
4. `autodev/server/routers/process.py` 返回字段；前端 `pipeline.js` 与 `missions.js` 使用原因和能力字段，不再只判断 `status === 'STALE'`。
5. `missions.view()` 也复用同一结果。当前仅根据检查存在与否等条件推导 `WAITING_APPROVAL`，需要防止存在严重发现时标题仍说“已准备好”。这是代码检查发现的潜在不一致，需补测试验证。

**保持安全语义：**页面显示 `PENDING` 不代表允许批准；服务端必须在提交决定时再次检查当前目标、轮次、来源和前置条件。对已批准但当前检查失效的记录，可以保留历史决定，同时将当前有效性标为 false。旧版本的批准不得自动继承到新规格。

### 5.3 验收

扩展 `tests/test_process_gates.py`、`tests/test_missions.py`、`tests/test_anti_fragmentation_probes.py` 和前端行为测试。至少覆盖：

1. 同一规格检查运行中，内容仍有效、批准禁用、提示准确；检查完成后无需重生成即可批准。
2. 只重跑同一规格的质量检查，不因读取状态生成多余审批轮次。
3. 答案变化、文档变化、外部文件改动，旧页提交仍被后端拒绝。
4. `CRITICAL`、缺失检查结果、未核验前置条件不能通过直接 HTTP 请求绕过。
5. 多个功能并存时指出具体阻塞功能，维持现有项目级审批范围，不偷偷改成功能级放行。
6. 页面刷新、数据库重新打开后状态一致；只读查询不改写文档或历史批准。

## 6. R4：把质量发现交给后续方案和一致性检查

### 6.1 代码检查发现的缺口

`adapter.run_step()` 的 `plan` 上下文依赖目前只有宪章和规格，`analyze` 依赖宪章、规格、方案和任务，没有明确带入当前质量清单及其结构化发现。发现存储在 `speckit.analysis:<checklist_rev_id>`，不能假设后续模型能自动看到。

主面板 `missions.js` 没有直接展示结构化发现。`routers/speckit.py` 返回来源及 `last_step`，但后续步骤会更新 `last_step`，不能用它充当稳定的质量发现记录。

### 6.2 最小修改

1. API 按当前 checklist 修订返回 `quality_review`，含修订号、对应规格来源、各级数量、逐条内容、关联需求和是否过期。缺失检查结果与空发现数组必须区分。
2. 主面板增加“质量检查结果”折叠区。当前提醒和历史提醒分开，默认显示数量和下一步；不要把全部日志塞进业务界面。
3. `plan` 明确读取当前有效的清单和发现，要求方案增加“检查发现处理”表：发现标识、处理位置、如何验证、是否还需规格变更。
4. `analyze` 对照同一批发现验证处理情况。不能因为方案里写了“已处理”就视为已满足，需核对需求、接口、任务和测试映射。
5. 需要改变业务承诺的发现必须回到规格修订及重新批准。纯接口实现细节可以进入方案；涉及尚未确认的范围不能由方案编写者自行承诺。

第一版可用 `checklist_rev_id + 数组序号` 作为稳定的发现引用，不必让模型凭空生成全局唯一编号。原始发现保持不可变；处理结论存在方案正文及其修订中，不回写覆盖原始模型结果。

### 6.3 输入版本必须同步管理

`service.input_fingerprint()` 目前未把 checklist 纳入 plan 和 analyze 的来源链，`publish_revision()` 对 checklist 的下游失效列表为空。新增上下文时应同时修改这两处，并检查派发签名、缓存命中与工作包冻结检查。

原则是：计划用了哪一版检查，就必须保存并签入那一版来源。检查内容或适用规格发生变化时，相关下游结论不得继续冒充当前结果。只把清单拼进提示词，却不改变来源签名，会留下迟到旧结果和错误复用问题。

已有计划或已冻结任务采用显式迁移与重新审阅，不能后台静默重编译或重派。本次试点没有开发任务，可以在保留历史后重新生成相关资料。无内容变化的检查重复操作应尽量复用同一结果，避免无意义失效。

### 6.4 宪章与规格的边界修正

本次宪章含具体 `REQ-001` 至 `REQ-004`，还新增了 `NFR-001`，功能规格却只登记了五条 REQ。编译器从功能规格提取需求，所以仅写在宪章里的 NFR 不会自然进入覆盖检查。

建议调整 Vernal 自有 preset：宪章保存原则、治理和兼容底线，功能规格作为可执行需求的唯一登记来源。适用的强制原则在规格中落实为明确 REQ/NFR，并保持映射，避免两份文档各维护一套业务条目。

不要通过删除已有兼容要求来消除警告。当前项目先显式补入适用的 NFR 或记录经负责人确认的适用范围；未来模板避免自动创造未经需求支持的额外 P0 承诺。

若修改 `autodev/assets/speckit/presets/vernal-core.json` 或 `vernal-lite.json`，应同步更新 preset 版本、`manifest.json` 哈希及验证记录。已锁定项目使用自己的资产副本，仓库模板变化不会自动升级它。通过显式资产升级流程迁移，或用新测试项目验证新版；不得直接改锁定副本、删除资产锁或改上游 vendored 文件掩盖差异。

## 7. R5：试点规格七条提醒逐项处理

以下方案针对当前最小回答保存试点。两项已确认条件保持不变：有效选项必填、补充说明可空；有效改答更新原记录。其余新增边界是建议，需在试点规格中显式记录，不代表已被用户批准的正式产品承诺。

| 提醒 | 应如何修改 | 修改位置与验收 |
| --- | --- | --- |
| W1 保存成功与失败反馈不明确 | 成功仅在保存完成后显示；校验拒绝和写入失败不得显示成功，已有保存内容不被覆盖 | 补 REQ-001、REQ-002、REQ-005；模拟提交失败，核对反馈与保存状态 |
| W2 已有记录时全空提交缺少独立验收 | 在已有有效记录状态下提交全空回答，拒绝提交，记录数仍为 1，选项和说明均保留原值 | 补 REQ-002 验收，不新增独立业务功能 |
| W3 首次保存、空值和内容相等口径不清 | “首次保存”以该题无已保存记录为准；无效提交后仍可首次成功保存。统一空值和相等规则 | 修改 REQ-001 的措辞，在输入契约写明规范化规则，并测试失败后再成功 |
| W4 重试去重未明确 | 同题同内容的重复请求和同一逻辑提交重试保持一条记录；不同有效内容按已确认规则更新 | 扩充 REQ-003，不引入完整请求历史或复杂分布式队列 |
| W5 保存、读取接口和异常语义缺失 | 明确有效选项归属、无记录、输入非法、保存失败、读取失败；不能把读取失败显示成无记录 | 放入 plan 的接口与数据及验证章节；用户可观察的行为写回规格 |
| W6 NFR-001 兼容要求没有进入规格 | 在规格登记首版格式基线及适用兼容要求，首版没有旧样本时明确标记适用性，不虚报升级验证 | 增加可解析的 NFR-001 和独立验收，后续格式变更才运行对应旧格式样本迁移测试 |
| W7 P0 需求、接口与自动化用例没有双向映射 | 建立五条 REQ 和适用 NFR 对应的逻辑操作、任务和实际测试位置；未实现的测试明确标待实现 | 放入 plan，编译前校验覆盖，编码后保存真实测试输出 |

### 7.1 建议的最小输入与保存契约

这些是便于实施的试点默认建议，正式采用前写入规格或方案，并明确属于负责人决策还是工程细节：

1. 以稳定题目 ID 关联回答，以稳定选项 ID 校验其属于该题。页面可以显示文本，提交边界不能只凭任意标签字符串判有效。
2. 补充说明缺省或空值统一为 `""`，其余内容按原文保存，不自动去空格或做 Unicode 规范化。相同内容指同题、同选项、规范化后的说明逐字一致；纯空白说明属于可保存说明，不影响选项必填。
3. 说明长度建议沿用当前界面已有的 10000 字符上限，但需定义为 Unicode 码点，并让前后端一致。JavaScript 的 `.length` 与 Python 字符串长度对部分字符的计数不同，边界测试须包含 emoji。若选择其他口径，也要在两端明确一致。
4. 同题只保存一条当前回答。重复请求不增加记录，有效改答更新该条记录。实现选用原子更新或唯一约束，不以“先查后插”的两个无保护操作承诺去重。
5. 最小读取结果区分无记录、有回答、读取失败。读取失败时保留可重试提示，不伪装首次填写。保存失败时保留用户当前输入，并保持最后成功保存的数据。
6. 首版可把刷新承诺限定在当前明确的项目与使用环境内，跨设备同步、关闭浏览器后恢复、设备迁移等必须分别说明适用范围。原需求只确认刷新，不得自行宣称全部支持。

不要在此处硬编码尚未确定的 HTTP 路径、数据库选型或框架。复用目标项目已有技术栈。若目标是 Vernal 本身，使用其现有服务端工作区及持久化机制，不另做一套浏览器存储系统。

| 用例 | 初始条件和操作 | 必须观察的结果 |

| A02 | 无记录，有效选项和空说明 | 保存成功，说明为空 |
