# P2 实现与自审记录

日期：2026 年 11 月 26 日。分支：`codex/standard-delivery-p2`。

## 结论与验收边界

P2 的需求入口、语义评估、澄清持久化、自动继续、轻量流程和执行前检查已实现。代码基于 P0/P1 发布基线 `7fe0ecb`，在独立 worktree 开发，没有修改原始主目录与 P0/P1 工作区。

本批不能宣布真实模型黄金试点已经通过。初次尝试启动 P2 服务时，执行环境拒绝监听 `127.0.0.1:8790`，错误为 `operation not permitted`。随后用户在自己的终端启动了该服务，真实页面验收已执行，并修复了提交按钮无法恢复的问题。后台身份也已接通现有执行服务；本机 Runner 仍离线，公共沙箱镜像和公用执行账号仍未就绪。详见 `P2_LIVE_ACCEPTANCE.md`，页面验证与真实模型交付分别记录。

## 已实现

| 能力 | 实际实现 |
| --- | --- |
| 统一输入 | 新建项目、接入目录、Git 仓库、浏览器导入均可保存研发目标和任务类型，复用已有创建与绑定接口 |
| 项目来源与清晰度分离 | 来源由项目元数据确定；模型分别判断目标、范围、验收、影响面和风险，后端计算清晰度，不根据字数分级 |
| Spec Kit 使用位置 | 使用固定版本的 clarify/specify 方法与规格模板进行准入评估，再调用现有 constitution、checklist、plan、tasks、analyze 适配步骤 |
| 执行主干 | 所有模型调用继续走 LoopForge 规划 SOP，保存原生 Issue、Run 和派发收据；没有新增执行器或审批系统 |
| 澄清 | 每轮最多三题，可以零题；关键决策暂停，低风险默认值折叠展示并可修改 |
| 回答与修订 | 批量回答先完整校验，再保存为同一个新规格修订；保留选项、补充原文和变更 Diff |
| 回答后的继续 | 自动重新评估；需要整理正文时保存新修订，保留需求编号和负责人回答原文；遇到需求审批停止 |
| 防止旧批准继续生效 | 输入、规格或回答变化后，旧评估不再允许批准开工；规格质量检查中的严重问题也会阻断 |
| 前置条件 | 外部账号、硬件等条件独立展示，记录负责人提供的核验依据；不得把核心验收标成后续体验项 |
| 轻量流程 | 明确的局部低风险需求可采用 vernal-lite 与 quick-prototype，取消独立详设阶段，保留规格、方案、验证、审查与合入门禁 |
| 执行前检查 | 只读检查后台执行身份、连接、执行机、沙箱和角色模型配置；不创建公用身份，不切换默认 Runner，不暴露凭据 |
| 恢复与防重发 | 持久保存阶段结果与项目执行租约；中断恢复先检查未终结的原生派发收据 |
| 任务发布 | 复用 P1 编译器与冻结工作包，在现有工作台确认方案和启动执行 |
| 界面 | 目标输入与澄清面板成为主要入口，旧单步与圆桌操作收进高级区域；公共模型未配置时不再显示虚构的默认型号 |

## 保留的边界

1. `vernal-standard`、`vernal-existing` 完整预设和条件式圆桌仍未实现。复杂项目采用当前 `vernal-core` 和既有标准门禁，页面展示限制。
2. 已锁定的项目预设和既有自定义流程不会因重新评估而静默替换。由模糊需求澄清后被推荐为轻量的项目，可能仍保留先前的保守流程。完整资产升级和存量流程迁移不在本批执行。
3. `quick-prototype` 复用当前独立验证及审查能力。P4 的增强确定性质量门、两阶段审查和收敛机制没有伪装成已完成。
4. 已冻结工作包仍不能原地替换。资源锁、运行中需求变更传播和重编译由 P3 继续处理。
5. 前置条件的人工核验依据会标明提供人。记录依据不代表平台实际连通或测试过外部系统。
6. 预检查通过仅表示允许尝试派发，不能代表真实模型执行成功；最终仍需原生执行收据与候选验证。
7. 整体布局重构和完整离线 Markdown 渲染由 P5 收敛；本批只调整需求和澄清交互面。

## 自审修正

1. 将逐题提交改为整轮先校验再发布，避免无效回答导致部分保存或工作副本漂移。
2. 把重新评估和质量检查加入现有文档门禁判定，防止用户答完后直接复用旧批准。
3. 在网络调用前预留项目执行租约，避免双击和并发请求产生重复派发。
4. 中断或超时后，只要原生收据仍待确认，就阻止新一轮规划，避免同时运行旧任务与新任务。
5. 宪章生成期间再次检查输入版本，避免后续步骤把新输入错误归到旧评估中。
6. 澄清后的规格整理保留原需求编号、负责人回答和补充原文，不能由模型覆盖这些确认记录。
7. 页面忽略切换项目后的迟到响应；输入草稿和回答 Diff 在页面刷新期间保留。

## 恢复真实验收

在本分支目录运行：

```bash
./scripts/start_p2_review.sh
```

脚本使用现有 Python 环境，服务地址为 `http://127.0.0.1:8790`。默认启动入口工作区，不再把澄清夹具写入未绑定的工作区。网页登录后先创建独立验收项目，再进入“继续需求交付”。本脚本不会调用模型、自动批准门禁或启动研发任务，也不会替代 Runner 的启动。

如需人工构造的页面夹具，先在网页创建独立项目，再指定它的真实工作区。只适用于没有规格和研发任务的测试项目，已有规格及回答不会被重置：

```bash
VERNAL_REVIEW_WORKSPACE="$PWD/workspaces/p2-clarify-acceptance" \
  ./scripts/start_p2_review.sh --fixture --prepare-only
```

使用已有部署的后台身份时，可在启动服务前通过 `VERNAL_SERVICE_TOKEN_FILE` 显式指定同一执行服务的身份文件。文件必须为非符号链接的私有权限文件。脚本不会签发新身份或打印凭据。

实际链路需具备已绑定项目、后台执行身份和在线 Runner，或可用的公共沙箱。当前页面检查已完成，待 Runner 上线后继续最小功能的实际模型交付，保存真实 Run、候选版本和验证结果。当前不把黄金试点 A 的真实执行验收勾选为完成。
