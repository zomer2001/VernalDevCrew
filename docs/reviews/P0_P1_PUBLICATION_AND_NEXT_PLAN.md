日期：2026 年 11 月 26 日。

## 当前结论

P0、P1 已具备更新到远端开发分支的代码基础。完整 P1 树的自动化结果为 257 项 Python 测试和 3 项前端测试通过。P0 已完成真实页面与接口验收；P1 的完整规划和执行协议使用模拟 HTTP 服务验证，真实模型、Runner、Docker 运行及新版页面仍需补齐。

## 下一批先解决什么

最高优先级是把现有能力连成可持续使用的真实交付流程。当前 P1 能阻止错误执行，但面对已发布任务的规格变化主要采用阻断，普通用户还需要理解和选择多个规格步骤。因此下一步同时面临真实执行可用性和入口易用性两个问题。

建议按下列顺序推进。每批完成代码、测试、实际证据和使用说明后再进入下一批；不以任务列表勾选代替实际结果。

| 批次 | 做什么 | 怎么做 | 完成依据 |
| --- | --- | --- | --- |
| P2 前置验收 | 补齐 P1 的真实模型和执行链路 | 从实际可用的一个执行池开始，在专用小项目走完规格、澄清、批准、计划、任务、编译、编码、验证、交付；保存 Run、候选内容和命令结果 | 至少一个执行器真实交付成功，失败可定位到模型、权限、依赖或产物校验，不用模拟结果代替 |
| P2A 统一入口 | 用户只说明做什么，无需自己选择七个技术步骤 | 新项目、本地目录和 Git 仓库进入同一任务输入页；明确执行池；评估来源、清晰度、类型和风险；低风险项采用有依据默认值 | 新手可从输入进入澄清，知道当前状态、下一步和阻塞原因；原有项目可继续打开 |
| P2B 黄金试点 | 用已有规格体系交付一个最小澄清功能增量 | 接上持久化问答、回答后修订、批准、编译和执行；轻量原型使用短规格与短计划；页面遵循原生工作台视觉 | 从一句话需求到可运行候选版本，全程有规格身份和验证依据 |
| P3A 安全变更与重编译 | 解决 P1 的阻断之后如何继续 | 保留已发布版本，新增工作包版本；区别未开始、运行中、已完成任务；契约变化要求依赖重新评估；稳定关联旧任务和替代任务 | 改需求后可以继续推进，既不复用过期结果，也不要求用户清库重建 |
| P3B 调度与争议处理 | 资源冲突、变更传播、必要时讨论 | 扩展编译校验，增加实际测试发现与工具链预检；引入资源锁和执行序号校验；只对具体争议追加圆桌质询 | 同资源写入不会并发冲突；无关任务可继续；迟到旧结果被拒收 |
| P4 质量与 Superpowers | 让开发和审查有可执行规范 | 按角色装配需求分析、TDD、系统调试和审查方法；确定性检查前置；区分需求符合性和代码质量审查；建立交付缺口收敛 | 错误复现是真的失败，测试确实运行，缺需求产生有依据的补缺任务，技能不自行调度或宣告交付 |
| P5 工作台统一 | 提升文档、执行流和审查体验 | 文档安全渲染和目录导航，交接结论优先展示，日志按需展开，统一阶段入口和原生抽屉，削减重复页面结构 | 核心流程点击顺畅、窄视口可用、文档和错误提示可读，满足 CSP 和离线资源约束 |
| P6 执行矩阵与离线 | 把一次跑通扩展为稳定支持 | 完成新建、存量、修复、重构、逆向模板；验证本机 Codex、沙箱 DSH、OpenCode；升级、重启恢复、断网加载及离线包分别测试 | 每种组合都有明确通过项与限制，不把模型联网和资源离线混为一谈 |

P2 前置验收先做一个执行器，避免同时修三种环境而无法定位问题。检测能力的最小改进随实际阻塞提前实现，完整执行器矩阵仍在 P6。

P3A 应先于复杂并发增强。用户能可靠地提出第二轮修改，比第一轮同时开更多 Agent 更重要。共享资源锁和条件圆桌在这个基础上增加。

## Spec Kit 后续如何持续使用

| 场景 | 规格动作 | 工程结果 |
| --- | --- | --- |
| 项目开始 | 建立并批准宪章，生成首个功能规格 | 形成项目约束及验收边界 |
| 需求不明确 | 澄清问题分类，持久保存回答并生成新修订 | 模型规划使用已确认答案，不丢失用户决策 |
| 每次功能增量 | 新功能目录或现有功能修订，再运行计划、任务、一致性检查 | 每轮实现有明确来源，不重复推倒全部架构 |
| 缺陷修复 | 描述期望行为、实际行为和复现条件，关联原需求 | 修复与需求身份对应，先确认可复现失败 |
| 运行中变更 | 比较新旧规格及契约，计算受影响工作包 | 执行继续或替换有依据，旧结果不会混入新交付 |
| 交付收敛 | 将当前规格与候选版本、测试证据对照 | 发现缺口时补任务；不能为了让测试通过而降低规格 |
| 老项目接管 | 现状摘录、增量规格和兼容边界 | 保留已有行为，明确本轮新增、修改和删除内容 |

轻量任务也保留规格与验收，只缩短文档和减少不必要步骤。工具版本继续按项目锁定，升级先做样板回归。

## Superpowers、OpenHands 与其他项目的位置

Superpowers 进入角色工作方法与质量步骤。平台仍负责身份、任务派发、工作区、批准和发布，技能不能另建同类控制链路。

OpenHands 先用于执行端设计参考，重点是能力探测、工作区边界、会话与恢复标识。是否引入其运行后端或 ACP，待真实执行链路稳定后用小范围对照实验决定。现阶段不把它作为新增必需组件。

契约差异检测、API 边界测试、浏览器行为回归、可观测性和软件物料清单工具，在对应缺口出现时接入既有质量与 CI 层。每个工具都需要明确触发条件、输入、输出、失败责任和维护成本，避免只有安装清单而没有实际消费者。

## 之后的协作方式

每批使用独立分支，先实现、再自审、运行适当回归并保存证据。发布开发分支与对外稳定发布分开记录。测试环境中能自动完成的操作由助手完成，负责人可选择抽查页面和结果。

下一次开发的建议范围为 P2 前置验收加 P2A。先补真实交付证据，再改善用户入口；不同时重做整个页面、替换执行框架或展开全部并发机制。
